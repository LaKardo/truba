## Что осталось

1. **Настоящий sysupgrade.** DNS сети после прошивки, установка пакетов из фида, подъём Туннеля после перезапуска сети.
2. **Приёмка на живой сети.** Тест 1 — NatTypeTester с ПК (сейчас проверено только через STUN Роутера: IP Трубы, порт сохраняется, отображение одинаково у двух серверов). Тесты 2 и 3 пройдены; 4–6 не проводились.
3. **Аппаратное ускорение.** Опыт проведён 2026-11-13, результаты — в разделе [«Опыт с ускорением»](#опыт-с-ускорением): Маршрутизация и Full cone NAT его переживают, учёт трафика — нет, через Туннель выигрыша нет. Оно остаётся выключенным (§4.2 architecture), пока не проверены Аварийная блокировка при ускоренных соединениях, устройства Wi-Fi и работа дольше нескольких минут.

## Опыт с ускорением

Опыт 2026-11-13 на NC-1812: ImmortalWrt 25.12.2, ядро 6.12.103, `firewall4` 2025.03.17, `truba` 1.2.0-r9. Режимы включались по очереди опциями `flow_offloading` и `flow_offloading_hw` в `firewall.@defaults[0]`, после опыта возвращена исходная настройка (оба выключены).

**Как мерили.** ПК в `lan` по кабелю 1 Гбит/с качал по HTTPS в 4 соединения 15 с; Роутер 10 с из них считал загрузку процессора по `/proc/stat`. «Напрямую» — файл с российского зеркала, Туннель — файл с узла рядом с Трубой. По два прогона на режим и путь. Скорость во всех режимах упиралась в канал провайдера (215–235 Мбит/с), поэтому прирост скорости опыт не показывает — только нагрузку на процессор.

| Режим | «Напрямую»: процессор, всего | «Напрямую»: самое занятое ядро | Туннель: процессор, всего | Туннель: самое занятое ядро |
|---|---|---|---|---|
| Без ускорения | 14–16 % | 43–47 % | 27–30 % | 48–53 % |
| Программное | ~8 % | 17–18 % | 27–29 % | 44–46 % |
| Аппаратное | 0,5–0,6 % | ~1 % | 27–32 % | 41–49 % |

- **«Напрямую».** Программное ускорение снижает нагрузку примерно вдвое. При аппаратном соединения привязаны в ускорителе (PPE), и процессор почти свободен.
- **Туннель.** Выигрыша нет. fw4 не ставит `awg0` в flowtable ни в одном режиме: при программном в ней `br-lan` и `wan`, при аппаратном — порты `lan*`, интерфейсы Wi-Fi и `wan`. Ускоряется только направление от устройства в Туннель; шифрование AmneziaWG остаётся на процессоре.

**Что пережило ускорение.** Проверено в обоих режимах, соединения при этом были помечены в conntrack как `[OFFLOAD]` или `[HW_OFFLOAD]`:

| Проверка | Программное | Аппаратное |
|---|---|---|
| «Туннель» идёт через `awg0`, внешний IP — IP Трубы | да | да |
| «Напрямую» идёт через провайдера | да | да |
| Full cone через Туннель: UDP с ПК, одно отображение у двух STUN-серверов, порт сохранён, пакет третьего узла доходит до ПК | да | да |
| Перехват DNS | да | да |
| `tunnel-test`, Туннель поднят | да | да |
| Счётчики `stats`, «Напрямую» | не считают оба направления | не считают оба направления |
| Счётчики `stats`, Туннель | считают только к устройствам | считают только к устройствам |
| Счётчики интерфейсов `wan` и `br-lan` | считают | трафик «Напрямую» не видят |

Классификацию, NAT и Full cone проходят первые пакеты соединения — они идут через netfilter в любом режиме. Мимо правил идут пакеты уже установленного соединения, поэтому теряется только учёт трафика.

**Что не проверено.**

- Аварийная блокировка при ускоренных соединениях: для неё надо остановить Туннель на Трубе.
- Full cone при UDP-соединении, привязанном в PPE. На пути «Напрямую» пакет третьего узла до ПК дошёл, но соединение со STUN-сервером в PPE не привязалось (мало пакетов в секунду), и отвечал один сервер.
- Устройства Wi-Fi, отдача, скорость выше канала провайдера.
- Работа дольше нескольких минут в каждом режиме.
- Приёмочные тесты 2 и 6 в этих режимах.

**Замечено.** После выключения аппаратного ускорения одно открытое соединение другого устройства осталось привязанным в PPE и продолжало работать, пока не закрылось.

## Куда расти

Направления, у которых уже есть место в архитектуре (§10 [architecture.md](architecture.md#10-точки-расширения)) и условия в ADR («Пересмотреть, если»):

- **IPv6 в Маршрутизации** — когда провайдер даст IPv6 (ADR 0005).
- **Уведомления** о падении и подъёме Туннеля — отдельным пакетом по событию `truba.tunnel`.
- **Биты метки как настройка** — если другая служба займёт `0x0f000000` (ADR 0011).
- **Другие платформы** — новые `target/subtarget` в сборке (ADR 0004).

| № | Что | Как проверить | Ожидание |

| 1 | Full cone | ПК в `lan` с Политикой «Всё в туннель»; NatTypeTester (RFC 5780) с двумя STUN-серверами | Mapping и Filtering: *Endpoint Independent*; публичный IP = IP Трубы |
