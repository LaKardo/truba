# Маршрутизация выключена до явного включения владельцем Роутера

*   **Автор:** мейнтейнер проекта (черновик — EGM)
*   **Статус:** предложено
*   **Дата:** 2026-11-01
*   **Целевая версия:** `truba` и `luci-app-truba` 1.2.0-r8
*   **Основа:** бриф [concepts_brief_safe_install.md](../../concepts_brief_safe_install.md). В нём же сохранён прежний текст этого документа в виде RFC.

## Обзор

Пакет `truba` при установке сразу запускает свою службу. Служба применяет настройки по умолчанию: Маршрутизация включена, Режим «Всё в туннель», Аварийная блокировка включена. На новом Роутере Туннеля ещё нет. Поэтому служба отрезает от интернета устройства сети, а у самого Роутера пропадает DNS. Установка не может докачать остальные пакеты, и сеть возвращается только после удаления пакетов. Та же авария повторяется при автоматической переустановке пакетов после sysupgrade и при повторной установке после удаления.

Предлагаемое изменение:

*   Первая установка, в том числе повторная после удаления пакета, ставит Маршрутизацию выключенной. Служба `truba` не трогает IPv4-трафик и DNS сети, пока владелец Роутера сам не включит Маршрутизацию. IPv6-интернет зон закрыт, как и раньше (ADR 0016).
*   Переустановка после sysupgrade на время установки выключает Маршрутизацию. Прежнее значение возвращается, только если модуль ядра AmneziaWG установился.
*   LuCI просит подтверждения, если включение Маршрутизации оборвёт интернет или его часть. Когда Туннель готов, а Маршрутизация выключена, «Обзор» подсказывает следующий шаг.

### Термины

| Термин | Значение |
|---|---|
| Роутер | Домашний роутер на ImmortalWrt, где стоят пакеты `truba` и `luci-app-truba` |
| Владелец Роутера | Человек, который ставит пакеты и настраивает Роутер. В документе — «владелец» |
| Труба | VPS на другом конце Туннеля (`CONTEXT.md`). Пакет и служба на Роутере называются «пакет `truba`» и «служба `truba`» |
| Туннель | Интерфейс AmneziaWG `awg0` между Роутером и Трубой |
| Маршрутизация | Переключатель `truba.main.routing`: решает ли служба, какой трафик пустить через Туннель |
| Аварийная блокировка | Переключатель `truba.main.killswitch`: если Туннель не работает, трафик Туннеля отбрасывается (`blackhole` в таблице маршрутов 77), а не идёт Напрямую |
| Напрямую | Через провайдера, мимо Туннеля |
| Режим | «Всё в туннель» (`mode=all`) или «Выборочный» (`mode=selective`) |
| Наборы правил, Категории | Файлы `geoip.dat`/`geosite.dat` и группы адресов из них, которым назначено Действие |
| Таблица 77 | Таблица маршрутов, куда служба отправляет трафик с меткой Туннеля |
| «Обзор», «Правила», «Туннель» | Вкладки LuCI. Строка состояния (в коде — `Hero`) — верхняя карточка «Обзора» с переключателями «Туннель» и «Маршрутизация» |
| postinst | Скрипт, который `apk` выполняет после установки пакета. Стандартный postinst OpenWrt включает и запускает службу |
| conffile | Файл настроек пакета (`/etc/config/truba`). При обновлении `apk` должен сохранять его, если владелец его менял |
| CUJ | Ключевой сценарий пользователя (critical user journey) |

## Проблема

**Что видит владелец.** Он выполняет команду установки из README: `apk add kmod-amneziawg amneziawg-tools luci-proto-amneziawg truba luci-app-truba luci-i18n-truba-ru luci-app-upnp`. На середине установки интернет пропадает у всех устройств. `apk` останавливается с ошибками загрузки, `luci-app-truba` не устанавливается, LuCI-страницы Трубы нет. Помогает только удаление пакетов через SSH. Владелец сначала заподозрил mosdns, потому что сбой случается сразу после его установки.

**Почему это происходит.** mosdns ни при чём: пакет mosdns выключает свой автозапуск, а сам mosdns запускает только служба `truba`. Причина в последовательности действий службы:

1. postinst включает и запускает `/etc/init.d/truba` посреди транзакции `apk`, раньше, чем `apk` доходит до `luci-app-truba`.
2. `truba apply` видит, что интерфейса Туннеля `awg0` нет. Служба лишь записывает предупреждение `tunnel_not_configured` и продолжает применение.
3. Загружается полная таблица nftables. В Режиме «Всё в туннель» весь трафик устройств получает метку Туннеля и уходит в таблицу 77.
4. Туннель не поднят, Аварийная блокировка включена, поэтому в таблице 77 стоит `blackhole default`. **Трафик устройств отбрасывается.**
5. dnsmasq перенастраивается на mosdns (сервер `127.0.0.1#5335`).
6. Запросы mosdns к DNS-серверам Туннеля несут метку Туннеля и тоже попадают в `blackhole`. **DNS Роутера не работает.**
7. `apk` не может разрешить имя репозитория и останавливается. Свой HTTPS-трафик Роутера метку не получает, сломано только разрешение имён.

**Тот же сбой после sysupgrade.** После прошивки `/etc/rc.local` запускает `/etc/truba/reinstall.sh` (ADR 0004). Сохранённый `/etc/config/truba` с `routing '1'` уже на месте. Скрипт ставит `amneziawg-tools luci-proto-amneziawg truba luci-app-truba` одной командой `apk add` и только после неё перезапускает сеть. Без перезапуска сети протокол `amneziawg` не загружен, Туннель не поднят. Служба стартует посреди транзакции, и шаги 3–7 повторяются. Значение по умолчанию здесь не помогает: файл взят из сохранённых настроек.

**Тот же сбой при повторной установке.** `uninstall.sh` удаляет `firewall.orig` и данные службы, но не `/etc/config/truba`. Файл изменён Стартовыми настройками, поэтому `apk del` может оставить его на месте. При повторной установке служба стартует со старым `routing '1'`, и шаги 1–7 повторяются. Именно так ставят пакеты владельцы, которых прежняя версия уже оставила без сети.

**Почему это важно.**

*   Первая установка — первое знакомство с Трубой. Сейчас она ломает сеть и оставляет систему полуустановленной, без LuCI-страницы.
*   Выйти из этого состояния владелец может, только понимая устройство службы или удалив пакеты.
*   Переустановка после sysupgrade идёт сама при загрузке, владелец её не видит и не может вмешаться.
*   Та же авария наступает всякий раз, когда Маршрутизация включена, Туннель не работает и Аварийная блокировка включена. Например, если `router.conf` импортирован, но сеть не перезапущена.

## Цели

*   **Первая установка не обрывает сеть.** На Роутере без интерфейса `awg0` команда `apk add …` из README доходит до конца. После неё:
    - устройства выходят в интернет Напрямую;
    - `nslookup` на Роутере отвечает;
    - в таблице 77 нет маршрута `default` (ни через Туннель, ни `blackhole`);
    - в dnsmasq нет сервера `127.0.0.1#5335`;
    - mosdns не запущен.
*   **Повторная установка после удаления не обрывает сеть.** Даже если от прежней установки остался `/etc/config/truba` с `routing '1'`, после установки Маршрутизация выключена.
*   **Переустановка после sysupgrade не обрывает сеть.** Все пакеты встают на место. Если модуль ядра AmneziaWG установился, `routing` после переустановки такой же, как до прошивки. Если нет — Маршрутизация остаётся выключенной, а в журнале записана команда, которой её вернуть.
*   **Маршрутизацию включает только владелец.** Первая установка не включает её. Обновление пакета сохраняет `routing`, если владелец менял `/etc/config/truba` или строки `routing` в файле нет. Импорт `router.conf` `routing` не меняет.
*   **LuCI предупреждает перед аварией.** Владелец включает Маршрутизацию на «Обзоре» или «Правилах», сохранённое значение — «выкл», Туннель не готов. Если включение оборвёт интернет или его часть (правило — §4), LuCI показывает подтверждение. «Отмена» ничего не меняет, переключатель остаётся выключенным.
*   **Понятный следующий шаг.** Когда Туннель готов, а Маршрутизация выключена, строка состояния «Обзора» показывает подсказку. Она не считается предупреждением.
*   **Сломанный прежней версией Роутер восстанавливается одной командой** без удаления пакетов. Команда описана в README.

«Туннель готов» означает: интерфейс поднят, служба не считает Туннель упавшим и есть свежее рукопожатие с Трубой (технический план, §4).

## Не-цели

*   **Флаг «вооружено»** (защита включается первым рабочим Туннелем). См. альтернативу D.
*   **Изменение поведения Аварийной блокировки.** Для Туннеля, который работал и упал, `blackhole` остаётся, как сейчас. Умолчание `killswitch=1` тоже не меняется (альтернатива J).
*   **Возврат Маршрутизации после sysupgrade по рукопожатию.** Если модуль ядра установился, а VPS временно не отвечает, `reinstall.sh` всё равно возвращает `routing=1`, и срабатывает Аварийная блокировка, как и задумано для упавшего Туннеля.
*   **Проверка при включении через CLI.** `uci set truba.main.routing=1` проходит без предупреждения. README описывает, как вернуть сеть.
*   **Прочие пути к аварии из LuCI.** Подтверждение спрашивается только в момент включения переключателя «Маршрутизация». Без подтверждения остаются:
    - выключить переключатель «Туннель» и включить Маршрутизацию в одном сеансе, до «Применить»;
    - включить Маршрутизацию при выключенной Аварийной блокировке и не поднятом Туннеле, а затем включить блокировку на вкладке «Туннель».

    Проверка итогового состояния при «Применить» рассмотрена и отклонена (альтернатива L).
*   **Автоматическое включение Маршрутизации** после импорта `router.conf` или первого подъёма Туннеля (альтернатива E).
*   **Отмена прочих изменений установки.** Full cone NAT, выключенное аппаратное ускорение, зона `truba`, перенаправления в неё и правила, закрывающие зонам IPv6-интернет (ADR 0016), остаются как сейчас и при выключенной Маршрутизации. IPv4 они не ломают, установку тоже.
*   **Прямое разрешение имён репозитория `apk` через mosdns** (`router_hosts`). См. альтернативу I.
*   **Изменение умолчаний `mode` и `dns_hijack`.** Они начинают действовать только после включения Маршрутизации.

## Открытые вопросы

*   **Вопрос 1. Как `apk` в ImmortalWrt 25.12 обращается с conffile при обновлении.** Решение без миграции опирается на то, что изменённый `/etc/config/truba` сохраняется. Проверяет это тест обновления в `build.yml` (план реализации, п. 19–20). **Условие выпуска:** тест прошёл; пропуск допустим, только пока в опубликованном фиде нет ни одной версии. Если тест покажет, что `apk` заменяет изменённый файл, до выпуска включается альтернатива G (вариант с `good/meta.json`).
*   **Вопрос 2. Ставится ли `truba` на образ x86-64 в тесте обновления.** `truba` зависит от `amneziawg-tools`, а он есть только в фиде mediatek/filogic. Нужно проверить на этапе реализации, есть ли пакет в фиде образа; если нет — тест ставит пакет-заглушку (план реализации, п. 19).

### Принятые решения

*   **Решение «подтверждать или нет» принимает только LuCI** (`common.routingRisk`). Служба лишь отдаёт данные (§3–4).
*   **Без миграции через `good/meta.json` или маркер версии.** При обновлении единственная миграция — записать `routing '1'`, если строки нет. При первой установке `90-truba` всегда пишет `routing '0'` (§1).
*   **Риск при поднятом Туннеле без рукопожатия не зависит от Аварийной блокировки:** трафик уходит в Туннель, который не отвечает (§4).
*   **В Режиме «Выборочный» подтверждение спрашивается со своим текстом:** без Туннеля недоступны только Категории Туннеля (§4).
*   **`reinstall.sh` возвращает Маршрутизацию, только если установился `kmod-amneziawg`** (§2).
*   **Правила IPv6 не меняются.** Они остаются и при выключенной Маршрутизации, как требует ADR 0016.
*   **Подтверждение спрашивается в переключателе**, а не при «Применить» (альтернатива L).
*   **Переустановка после sysupgrade** временно ставит `routing=0` в `reinstall.sh` (§2).

## Ключевые сценарии (CUJ)

Тексты LuCI, на которые ссылаются сценарии, приведены один раз — в таблице строк, §4.

### CUJ 1. Первая установка на чистый Роутер

*   **Дано:** ImmortalWrt 25.12, интернет через `wan`, пакетов Трубы нет, интерфейса `awg0` нет.
*   **Когда:** владелец выполняет команду `apk add …` из README §3.
*   **Тогда:**
    - все пакеты установлены;
    - устройства и Роутер всё время в интернете;
    - `/etc/config/truba` содержит `routing '0'`, в `applied.json` — `routing: false`, `mosdns: false`;
    - в таблице 77 нет `default`;
    - «Обзор» показывает «Туннель не настроен».

### CUJ 2. Включение Маршрутизации после настройки Туннеля

*   **Дано:** CUJ 1 пройден, `router.conf` импортирован, сеть перезапущена, рукопожатие с Трубой свежее. Маршрутизация выключена.
*   **Когда:** владелец видит подсказку `ROUTING_IDLE` в строке состояния, включает переключатель «Маршрутизация» и нажимает «Применить».
*   **Тогда:**
    - подтверждения нет;
    - трафик идёт по Режиму, DNS — через mosdns;
    - если Наборы правил ещё не скачаны, первые минуты на «Обзоре» висит предупреждение «Наборы правил скачиваются», действует только Режим. После скачивания служба применяет настройки повторно, и Категории начинают действовать;
    - подсказки нет.

### CUJ 3. Включение Маршрутизации, когда Туннель не готов

*   **Дано:** Туннель не настроен, выключен, не поднят, не отвечает или поднят без свежего рукопожатия. Аварийная блокировка включена. Сохранённое значение Маршрутизации — «выкл».
*   **Когда:** владелец включает переключатель «Маршрутизация» на «Обзоре» или «Правилах».
*   **Тогда:**
    - LuCI показывает подтверждение `DLG_TITLE`. Текст: если Туннель поднят без рукопожатия — `DLG_TEXT_DEAD`; иначе в Режиме «Всё в туннель» — `DLG_TEXT_ALL`, в Режиме «Выборочный» — `DLG_TEXT_SEL`;
    - «Отмена» или Esc: переключатель снова выключен (и в UCI, и на экране), несохранённых изменений нет;
    - «Включить»: одно несохранённое изменение, как при обычном клике.

### CUJ 3b. Аварийная блокировка выключена

*   **Дано:** как в CUJ 3, но Аварийная блокировка выключена — сохранена или только что выключена в этом сеансе.
*   **Когда:** владелец включает «Маршрутизацию».
*   **Тогда:**
    - Туннель не настроен, выключен, не поднят или не отвечает: подтверждения нет. Трафик Туннеля идёт Напрямую, сеть не ломается.
    - Туннель поднят, но рукопожатия нет: подтверждение с текстом `DLG_TEXT_DEAD`. Watchdog ещё не объявил Туннель упавшим или выключен, в таблице 77 стоит `default dev awg0`, и трафик уходит в Туннель, который не отвечает.

### CUJ 3c. Возврат к сохранённому значению

*   **Дано:** сохранено `routing=1`, Туннель не готов. Владелец выключил переключатель, но не применил.
*   **Когда:** он включает переключатель обратно.
*   **Тогда:** подтверждения нет, несохранённых изменений нет.

### CUJ 4. Обновление пакета на работающем Роутере

*   **Дано:** прежняя версия, `routing=1`, Туннель работает.
*   **Когда:** владелец выполняет `apk upgrade truba luci-app-truba`.
*   **Тогда:**
    - `/etc/config/truba` сохраняет `routing '1'`;
    - трафик, DNS и Аварийная блокировка работают, как до обновления.

### CUJ 4b. Повторная установка после удаления

*   **Дано:** прежняя версия была установлена, `apk del truba luci-app-truba` выполнен, `/etc/config/truba` с `routing '1'` остался.
*   **Когда:** владелец ставит новую версию командой из README.
*   **Тогда:** как в CUJ 1, `routing '0'`. Категории из оставшегося файла сохранены.

### CUJ 5. Переустановка после sysupgrade

*   **Дано:** версия r8 или новее, `routing=1`, Туннель работал. Владелец прошивает новую ImmortalWrt с сохранением настроек.
*   **Когда:** после загрузки `reinstall.sh` ставит пакеты.
*   **Тогда:**
    - все пакеты установлены, во время установки DNS Роутера работает;
    - в журнале запись `truba-reinstall` «Маршрутизация выключена на время установки»;
    - если `kmod-amneziawg` установился: после перезапуска сети `routing` снова `1`, в журнале «Маршрутизация возвращена»;
    - если `kmod-amneziawg` под новую версию в фиде нет: `routing` остаётся `0`, сеть работает Напрямую, в журнале команда, которой вернуть Маршрутизацию после установки модуля.

### CUJ 6. Восстановление Роутера, сломанного прежней версией

*   **Дано:** установлена прежняя версия, интернет пропал (`routing=1` без Туннеля, Аварийная блокировка включена), SSH по LAN работает.
*   **Когда:** владелец выполняет команду из раздела README «Пропал интернет после установки или включения Маршрутизации»: `uci set truba.main.routing=0 && uci commit truba && /etc/init.d/truba reload`.
*   **Тогда:**
    - в таблице 77 нет `blackhole`, dnsmasq без mosdns, DNS отвечает;
    - `apk` может доустановить пакеты.

### CUJ 7. Маршрутизация выключена намеренно

*   **Дано:** Туннель готов, владелец держит Маршрутизацию выключенной, например ради входящих через IP Трубы (ADR 0014).
*   **Когда:** он открывает «Обзор».
*   **Тогда:** строка состояния показывает «Всё работает», предупреждений нет. Под переключателями — подсказка `ROUTING_IDLE` обычным серым текстом.

## Технический план

### Общая схема

Изменение затрагивает три части:

*   **Умолчание и переустановка:** `/etc/config/truba`, схема в `conf.uc`, `90-truba`, `reinstall.sh`.
*   **Ответ службы для «Правил»:** `state.uc` отдаёт состояние Туннеля.
*   **LuCI:** правило риска в `common.js`, переключатель с подтверждением в `kit.js`, подсказка на «Обзоре».

Логика маршрутизации, межсетевого экрана и DNS в службе не меняется. Ветка «Маршрутизация выключена» уже есть в коде и покрыта тестами.

```text
 установка / переустановка             LuCI (браузер)
 ─────────────────────────             ──────────────
 /etc/config/truba                     переключатель «Маршрутизация»
   routing '0' (первая установка)         │ выкл → вкл
   routing '0' на время apk add           ▼
     (reinstall.sh, затем прежнее,     сохранено «вкл»? → app.set, без вопроса
      если встал kmod-amneziawg)
        │                              common.routingRisk(st)
        ▼                                ├─ нет риска → app.set(routing=1)
 truba apply, cfg.routing == false       └─ риск → kit.Dialog
   ├─ урезанная таблица nftables               ├─ Отмена → ничего
   ├─ dnsmasq без mosdns                       └─ Включить → app.set(routing=1)
   ├─ mosdns не запущен
   ├─ таблица 77 без default            st = truba status
   └─ журнал: «Маршрутизация              «Обзор»: полный ответ, раз в 5 с
       выключена…» (при старте            «Правила»: part='rules', раз в 10 с
       и при выключении)
                                            + tunnel, awg, health (новое)
```

### 1. Значение по умолчанию, первая установка и обновление

**Умолчание.** `routing` задаётся в двух местах, и оба переходят на «выкл»: в поставляемом `/etc/config/truba` и в схеме `conf.uc`. Схема действует, если строки `routing` в UCI нет, и через `truba schema` доходит до LuCI (ADR 0015).

**Первая установка.** Её `90-truba` узнаёт по отсутствию `firewall.orig` (`FIRST=1`). В этом случае он всегда пишет `routing '0'`, даже если `/etc/config/truba` остался от прежней установки (CUJ 4b). Переустановку после sysupgrade это не затрагивает: `firewall.orig` лежит в сохраняемом `/etc/truba/`, там `FIRST=0`.

**Обновление.** `/etc/config/truba` — conffile. На работающем Роутере он почти всегда отличается от поставляемого: при первой установке `90-truba` дописывает в него Стартовые настройки. Изменённый файл при обновлении сохраняется вместе с `routing '1'` (открытый вопрос 1).

**Миграция для файла без строки `routing`.** Раньше без строки действовало «вкл», теперь подействовало бы «выкл». Поэтому при обновлении (`FIRST=0`) `90-truba` записывает `routing '1'`, если строки нет. Выбор владельца это не меняет.

**Остаточный риск** — файл побайтно совпадает с поставляемым прежней версией, например владелец удалил все Категории. Тогда `apk` может заменить его, и Маршрутизация выключится. Этот риск описан только здесь, остальные разделы ссылаются сюда. Меры:

*   тест обновления фиксирует фактическое поведение `apk` (п. 19);
*   служба пишет в журнал, что Маршрутизация выключена (§3);
*   CHANGELOG предупреждает: «проверьте переключатель после обновления».

### 2. Переустановка после sysupgrade

Правила для `reinstall.sh`:

*   До `apk add` скрипт запоминает `routing` и ставит «выкл». Служба, запущенная посреди транзакции, сеть не трогает.
*   Прежнее значение возвращается после `network restart`, только если `kmod-amneziawg` установился. Если VPS временно не отвечает, срабатывает Аварийная блокировка, как задумано для упавшего Туннеля.
*   Если модуля под новую версию ImmortalWrt в фиде нет, Маршрутизация остаётся выключенной: сеть работает Напрямую, и Роутер может докачать модуль, когда сборка появится. В журнале — команда установки модуля и возврата Маршрутизации.
*   Если не удалась установка пакетов, Маршрутизация тоже остаётся выключенной, в журнале — команда возврата.
*   Каждый шаг пишет запись `truba-reinstall` в журнал.

Если питание пропадёт посреди переустановки, Маршрутизация останется выключенной. Сеть работает, в журнале есть первая запись.

**Ограничение.** `reinstall.sh` лежит в `/etc/truba/`, а этот каталог sysupgrade сохраняет. После прошивки работает та версия скрипта, что стояла до неё. Значит, защита действует с первой прошивки после обновления до r8. Роутеру, прошитому прямо с r7, помогает раздел README из CUJ 6.

Две транзакции (сначала `amneziawg` и `network restart`, потом `truba`) не помогают: без `kmod-amneziawg` под новую версию ImmortalWrt Туннель всё равно не поднимется.

### 3. Служба

**Журнал.** Служба пишет одну строку уровня `info`, когда применяет настройки с выключенной Маршрутизацией, а в прошлом применении она была включена или его не было. `applied.json` лежит в оперативной памяти, поэтому строка появляется и при каждом старте службы, то есть раз на загрузку. Повторные применения с `routing=0` ничего не пишут.

**Ответ `status(part='rules')`.** Вкладке «Правила» для правила риска нужны те же данные о Туннеле, что «Обзору»: `tunnel` (настроен, выключен, поднят, рукопожатие) и `health`. Ветка `part == 'dns'` не меняется.

### 4. LuCI

**Состояние Туннеля.** `common.tunnelState(st)` уже возвращает уровень и подпись:

| Входные данные `st` | Уровень | Подпись |
|---|---|---|
| нет поля `service` | `''` | «нет данных» |
| `service == false` | `err` | «служба остановлена» |
| `tunnel.configured == false` | `warn` | «не настроен» |
| `tunnel.disabled` | `warn` | «выключен» |
| `tunnel.up == false` | `err` | «не поднят» |
| `health.state == 'down'` | `err` | «не отвечает» |
| иначе | `ok` | «работает» |

Уровень `ok` не означает, что Туннель пропускает трафик: интерфейс AmneziaWG поднимается без единого рукопожатия. Watchdog объявляет «не отвечает» только после нескольких неудачных проверок (около 90 с), а если он выключен — никогда. Всё это время в таблице 77 стоит `default dev awg0` (`net.uc:70-72`), и трафик уходит в Туннель независимо от Аварийной блокировки.

**Туннель готов** (`tunnelReady`) — уровень `ok` и рукопожатие было, не старше порога watchdog `handshake_max` (из `health.json`, а без него — из UCI). Keepalive Туннеля — 15–25 с, поэтому у работающего Туннеля рукопожатие свежее.

**Правило риска** (`routingRisk`) — подтверждать ли включение и каким текстом:

| Состояние | Аварийная блокировка | Подтверждение |
|---|---|---|
| нет данных или ответ прежней службы без `tunnel` | любая | нет |
| Туннель готов | любая | нет |
| `ok`, но рукопожатия нет или оно старое | любая | да, `DLG_TEXT_DEAD` |
| не настроен, выключен, не поднят, не отвечает | вкл | да, `DLG_TEXT_ALL` или `DLG_TEXT_SEL` по Режиму |
| не настроен, выключен, не поднят, не отвечает | выкл | нет |

Аварийная блокировка и Режим берутся из UCI браузера, поэтому учитываются и несохранённые изменения. `DLG_TEXT_DEAD` тоже зависит от Режима только словами «весь трафик» и «трафик Категорий Туннеля».

**Переключатель «Маршрутизация»** (`RoutingSwitch`) на «Обзоре» и «Правилах»:

*   Подтверждение спрашивается только при переходе «выкл → вкл», когда сохранённое значение — «выкл». Возврат к сохранённому «вкл» сеть не меняет (CUJ 3c).
*   «Отмена» и Esc: UCI не меняется, флажок на экране возвращается в «выкл».
*   Выключение подтверждения не требует.

**Подсказка на «Обзоре».** Если Маршрутизация выключена (с учётом несохранённого), а Туннель готов, строка состояния показывает под переключателями `ROUTING_IDLE` серым текстом. Подсказка не входит в предупреждения: не увеличивает их счётчик и не меняет уровень строки состояния (CUJ 7).

**Строки.** Новые msgid — в `po/templates/truba.pot`, перевод — в `po/ru/truba.po`. Это единственное место, где приведены тексты:

| Имя | msgid | Русский текст |
|---|---|---|
| `DLG_TITLE` | Turn on routing while the tunnel is not ready? | Включить Маршрутизацию, пока Туннель не готов? |
| `DLG_TEXT_ALL` | Tunnel: %s. Emergency block is on: until the tunnel works, devices on the network and the router itself will have no internet. Set up the tunnel first or turn off Emergency block on the Tunnel tab. | Туннель: %s. Аварийная блокировка включена: пока Туннель не заработает, устройства сети и сам Роутер останутся без интернета. Сначала настройте Туннель или выключите Аварийную блокировку на вкладке «Туннель». |
| `DLG_TEXT_SEL` | Tunnel: %s. Emergency block is on: until the tunnel works, sites from tunnel categories will be unreachable. Everything else goes direct. | Туннель: %s. Аварийная блокировка включена: пока Туннель не заработает, сайты из Категорий Туннеля будут недоступны. Остальное идёт Напрямую. |
| `DLG_TEXT_DEAD` | The tunnel is up, but there is no handshake with Truba: %s will go into a tunnel that does not respond. Check the server and the tunnel settings first. | Туннель поднят, но рукопожатия с Трубой нет: %s уйдёт в Туннель, который не отвечает. Сначала проверьте сервер и настройки Туннеля. |
| — (для `DLG_TEXT_DEAD`, Режим «Всё в туннель») | all traffic | весь трафик |
| — (для `DLG_TEXT_DEAD`, Режим «Выборочный») | traffic of tunnel categories | трафик Категорий Туннеля |
| `DLG_OK` | Turn on | Включить |
| `ROUTING_IDLE` | The tunnel works, but routing is off: all IPv4 traffic goes direct. Turn it on in the status bar. | Туннель работает, но Маршрутизация выключена: весь IPv4-трафик идёт Напрямую. Включите её в строке состояния. |

## Рассмотренные альтернативы

### Альтернатива A. Запускать mosdns после старта службы `truba`

*   **Плюсы:** не меняется поведение по умолчанию.
*   **Минусы:** так уже сделано. Пакет mosdns выключает свой автозапуск, `90-truba` это повторяет, а запускает mosdns только служба `truba` после `truba apply`.
*   **Почему отклонена:** интернет обрывают `blackhole` в таблице 77 и перенаправление dnsmasq. Порядок запуска mosdns на них не влияет.

### Альтернатива B. Служба не трогает сеть, пока нет интерфейса Туннеля (`tinfo.exists`)

*   **Плюсы:** одна строка в `apply_config`. Умолчание `routing=1` остаётся. После импорта Маршрутизация включается сама.
*   **Минусы:**
    - Не закрывает окно «интерфейс есть, протокол `amneziawg` ещё не загружен»: после импорта до `network restart` и при переустановке после sysupgrade.
    - Если на работающем Роутере удалить интерфейс Туннеля, Аварийная блокировка молча отключится.
    - Пересчёт маршрутов из hotplug и watchdog читает UCI заново и обошёл бы проверку.
    - В UCI `routing=1`, а на деле ничего не маршрутизируется. LuCI показывал бы неправду.
*   **Почему отклонена:** закрывает только часть случаев и добавляет скрытое состояние.

### Альтернатива C. Проверка по `tinfo.up`

*   **Плюсы:** закрывает и окно до `network restart`.
*   **Минусы:** при каждой загрузке Роутера и каждом падении Туннеля трафик шёл бы Напрямую.
*   **Почему отклонена:** Аварийная блокировка теряет смысл.

### Альтернатива D. Флаг «вооружено»: защита включается первым рабочим Туннелем

*   **Плюсы:** умолчание `routing=1` остаётся. Защищает и от включения через CLI. Различает «Туннель ещё не работал» и «Туннель упал».
*   **Минусы:**
    - Постоянный флаг на флеше и миграция для установленных Роутеров.
    - Новые поля в `applied.json`. Все потребители (`net.routes`, `cron_set`, `state.uc`, `check.uc`) переходят на `applied` вместо UCI.
    - Новый ADR о смысле Аварийной блокировки.
*   **Почему отложена:** для первой установки та же польза достигается умолчанием и подтверждением в LuCI. Вернуться, если владельцы будут включать Маршрутизацию через CLI без Туннеля.

### Альтернатива E. Включать Маршрутизацию при импорте `router.conf`

*   **Плюсы:** нет лишнего шага.
*   **Минусы:**
    - Импорт начинает менять настройку владельца.
    - Сразу после импорта Туннель ещё не работает (нужен `network restart`), и авария наступила бы в момент импорта.
    - Пользователь CLI об этом поведении не знает.
*   **Почему отклонена:** переносит аварию, а не устраняет её.

### Альтернатива F. Запретить включение, пока Туннель не готов

*   **Плюсы:** из LuCI оборвать сеть нельзя.
*   **Минусы:**
    - Владелец может сознательно хотеть «всё заблокировано, пока нет Туннеля», например, если Роутер ставят заранее, а VPS появится позже.
    - Статус приходит раз в 5–10 с: переключатель был бы неактивен, когда Туннель уже готов.
*   **Почему отклонена:** подтверждение предупреждает, но не запрещает. Ошибка опроса стоит лишнего вопроса, а не заблокированной настройки.

### Альтернатива G. Миграция `routing=1` при обновлении по `good/meta.json` или маркеру версии

*   **Плюсы:** работающий Роутер не теряет Маршрутизацию, как бы `apk` ни обращался с conffile.
*   **Минусы:**
    - Вариант с `good/meta.json` может включить Маршрутизацию вопреки владельцу, если его выключение не применилось.
    - Вариант с маркером не срабатывает в единственном важном случае — когда файл заменён целиком.
*   **Почему отклонена:** изменённый conffile сохраняется, а на работающем Роутере файл почти всегда изменён. Это запасной план, если тест обновления покажет обратное (открытый вопрос 1).

### Альтернатива H. Обходные пути `apk`: скачать всё заранее или ставить в два шага

*   **Плюсы:** без изменения кода.
*   **Минусы:** устраняют только сбой во время установки. После неё сети всё равно нет, пока не настроен Туннель.
*   **Почему отклонена:** с `routing=0` не нужна.

### Альтернатива I. Добавить серверы репозитория `apk` в `router_hosts`

*   **Плюсы:** при упавшем Туннеле и Аварийной блокировке Роутер всё равно может ставить пакеты.
*   **Минусы:** не спасает устройства сети. Нужно разбирать `/etc/apk/repositories*`. Меняет список своих хостов Роутера, видимый в «Куда пойдёт».
*   **Почему отклонена:** это отдельная задача для упавшего Туннеля, а не для установки.

### Альтернатива J. Умолчание `killswitch=0`

*   **Плюсы:** без Аварийной блокировки `routing=1` без Туннеля не ставит `blackhole`: трафик и DNS идут Напрямую, установка проходит. Лишнего шага нет.
*   **Минусы:**
    - Владелец, у которого Туннель потом упадёт, молча получит трафик Напрямую — утечку, от которой его защищало умолчание.
    - Сразу после установки служба всё равно перенаправляет DNS в mosdns и меняет маршрутизацию, хотя Туннеля нет.
*   **Почему отклонена:** ослабляет защиту всех ради первых минут после установки.

### Альтернатива K. Не запускать службу в postinst до импорта настроек

*   **Плюсы:** установка ничего не применяет.
*   **Минусы:**
    - Служба нужна LuCI (`ubus truba status`, `truba schema`) и входящим через IP Трубы (ADR 0014).
    - `reinstall.sh` запускает службу явно, этот путь остался бы открытым.
    - Стандартный postinst OpenWrt пришлось бы обходить.
*   **Почему отклонена:** ломает LuCI и не закрывает переустановку.

### Альтернатива L. Проверка риска при «Применить» по итоговому состоянию

*   **Плюсы:** покрывает все вкладки и любой порядок действий, включая выключение Туннеля в том же сеансе.
*   **Минусы:**
    - Вопрос появляется не в момент действия, а на панели изменений, когда владелец уже переключился на другое.
    - Меняется общий код применения всех вкладок (`handleSaveApply`).
    - Тот же вопрос нужен и для «Сохранить и применить» LuCI.
*   **Почему отклонена:** выбор мейнтейнера — проверка в переключателе; оставшиеся пути записаны в не-цели.

## Нефункциональные требования

*   **Безопасность и приватность.**
    - Пока Маршрутизация не включена после первой установки, IPv4-трафик идёт Напрямую. Туннеля ещё нет, защищать нечего. IPv6-интернет зон, как и раньше, закрыт (ADR 0016).
    - Маршрутизация может выключиться без участия владельца: остаточный риск обновления (§1), переустановка без `kmod-amneziawg` или прерванная переустановка (§2). Тогда IPv4-трафик и DNS идут Напрямую. Это видно в журнале, на «Обзоре» (переключатель и подсказка, если Туннель готов) и защищено тестом обновления и условием выпуска. При сбое переустановки выбрана работающая сеть, а не блокировка: иначе Роутер не может докачать модуль.
    - Аварийная блокировка при включённой Маршрутизации работает, как раньше.
*   **Откат и обновление.**
    - Обновление сохраняет `routing` (§1).
    - Откат на r7: прежняя версия читает `routing '0'` так же. После r8 строка `routing` всегда записана явно: `90-truba` и `reinstall.sh` пишут значение, а не удаляют строку.
    - `sysupgrade -n` (без сохранения настроек): Маршрутизация выключена, как при первой установке.
*   **Совместимость версий.**
    - Новый `luci-app-truba` требует `truba (>=1.2.0-r8)`.
    - Если ответ службы без поля `tunnel`, `routingRisk` возвращает `null`: подтверждения нет, а не ложное подтверждение всегда.
    - Прежний LuCI с новой службой работает, но без подтверждения и подсказки.
*   **Наблюдаемость.** Запись службы при старте и применении с выключенной Маршрутизацией (§3), записи `truba-reinstall` (§2). `truba status` по-прежнему отдаёт `routing`.
*   **Доступность.** Подтверждение — `kit.Dialog` на родном `<dialog>`: фокус внутри окна, Esc закрывает как «Отмена», заголовок связан через `aria-labelledby`. Фокус возвращает браузер.
*   **Локализация.** Новые msgid на английском, перевод на русский (§4, таблица строк).
*   **Производительность.** Ответ `status(part='rules')` дополнительно делает один вызов ubus, одно чтение `health.json` и, если Туннель поднят, запускает `awg` раз в 10 с, пока открыта вкладка «Правила». Нагрузка на Роутер заметно не меняется.
*   **Выпуск.** Тест установки и обновления в `build.yml` прошёл. Пропуск допустим, только пока в опубликованном фиде нет ни одной версии `truba`; иначе пропуск — ошибка, и фид не публикуется. Ручная проверка на Роутере (план проверки) выполнена.

#### 19. `tests/router/upgrade.sh` (создать)

*   **Что:** проверка настоящей установки и обновления через `apk`. Контейнер запускается с `/sbin/init`, как стенды в `tests/run.sh` (`stand`, `:98-109`), чтобы postinst действительно запускал службу. Тест вызывается из `build.yml`, где есть собранные `.apk`.
*   **Сеть.** Под procd у контейнера сети нет (`tests/run.sh:82`). Поэтому:
    - зависимости ставятся в образ заранее, как в `test_img` (`tests/run.sh:83-90`): `IMG` без init, `apk add` зависимостей `truba` из фида образа, `docker commit`;
    - прежняя версия `truba` и заглушка `amneziawg-tools` готовятся на раннере до запуска контейнера и монтируются каталогом;
    - внутри контейнера все `apk add` идут из локальных файлов (`--allow-untrusted`, без `apk update`);
    - wan — статикой по образцу `tests/luci/stand.sh:26-33`; DNS проверяется через локальный dnsmasq: `nslookup` к `127.0.0.1` имени, которое знает только он (`--address=/up.trubatest/…`, как в `life.sh:97`).
*   **Откуда прежняя версия.** `truba` собирается с `PKGARCH:=all`, поэтому `.apk` из фида mediatek/filogic ставится и на x86-64. Раннер скачивает `packages.adb` опубликованного фида, находит в индексе запись `truba` и её версию (`apk adbdump`), скачивает файл по имени `truba-<версия>.apk`. По шаблону имени файла не ищем.
*   **Заглушка `amneziawg-tools`** (открытый вопрос 2): если пакета нет в фиде образа x86-64, раннер собирает пустой пакет `apk mkpkg --info name:amneziawg-tools --info version:0-r0 --info arch:noarch` и ставит его с `--allow-untrusted`.
*   **Вход:** каталог с новыми `.apk`, каталог с прежней версией и заглушкой (готовит раннер), признак «в фиде есть версия».
*   **Случай 1. Чистая установка (CUJ 1):**
    - локальный каталог `.apk` подключается как репозиторий (`apk add --allow-untrusted --repository`);
    - `apk add truba luci-app-truba` одной командой;
    - проверки: оба пакета установлены; служба запущена; `/var/run/truba/applied.json` существует и содержит `routing: false`; `routing=0`; в таблице 77 нет `default`; `pidof mosdns` пусто; dnsmasq без `127.0.0.1#5335`, `nslookup up.trubatest 127.0.0.1` отвечает.
*   **Случай 2. Обновление изменённого файла (CUJ 4):**
    - прежняя версия, `uci set truba.main.routing=1`, `commit`;
    - убедиться, что файл отличается от поставляемого;
    - `apk add --allow-untrusted <новый>.apk`;
    - проверки: новая версия, `routing=1`, число секций `rule` прежнее. Если рядом лежит `/etc/config/truba.apk-new`, записать это в вывод.
*   **Случай 3. Файл без правок (контрольный):** новый контейнер, прежняя версия, файл приведён к поставляемому побайтно. После обновления вывести, какое значение `routing` получилось. Это фиксация поведения для остаточного риска, а не проверка.
*   **Случай 4. Удаление и повторная установка (CUJ 4b):** прежняя версия, `routing=1`, `apk del truba luci-app-truba`, `apk add` новой версии → `routing=0`, в таблице 77 нет `default`.
*   **Пропуск.** Если в опубликованном фиде нет ни одной версии `truba` (первая публикация), случаи 2–4 пропускаются с `::warning::`. Если версия в фиде есть, но скачать её не удалось, — ошибка.

#### 21. `docs/adr/0019-routing-off-until-owner-enables.md` (создать)

*   Статус «принято, <дата>». Разделы по `docs/adr/README.md`:
    - **Контекст:** цепочка аварии из раздела «Проблема», включая переустановку и повторную установку.
    - **Рассмотренные варианты:** кратко A–L со ссылкой на этот документ.
    - **Решение:**
        - `routing=0` в файле и схеме, первая установка всегда ставит `0`; включает только владелец;
        - LuCI подтверждает включение, если Туннель не готов, по правилу §4;
        - `reinstall.sh` выключает Маршрутизацию на время установки и возвращает, только если встал `kmod-amneziawg`;
        - миграция при обновлении — только для файла без строки `routing`.
    - **Последствия:** лишний шаг после импорта; CLI и прочие пути из не-целей без проверки; остаточный риск обновления; при сбое переустановки сеть идёт Напрямую, а не блокируется; защита переустановки — с первой прошивки после r8.
    - **Пересмотреть, если:** владельцы включают Маршрутизацию без Туннеля через CLI; `apk` заменяет изменённые conffile; появится автонастройка Туннеля при установке.
