# Трафик по устройствам: наборы nftables со счётчиками, история в оперативной памяти

- Статус: принято, 2026-10-12

## Контекст

Интерфейс показывает, кто в домашней сети сколько качает и через что: вкладка «Устройства» (скорость каждого устройства, доля Туннеля и Напрямую, график за час, объём за сутки) и число активных устройств на «Обзоре». Служба знала только общий объём по Действиям (цепочка `stats`, ADR 0010).

Счёт должен идти в ядре, как весь путь трафика (ADR 0002): процесс на каждом пакете NC-1812 не потянет. Цена — правила на каждом транзитном пакете; её замерили на NC-1812 до кода интерфейса.

## Рассмотренные варианты

- **Динамические наборы со счётчиком у элемента** (`flags dynamic,timeout; counter;`), адрес устройства добавляет `update` в правилах `stats`. Выбрано.
- **Счётчики conntrack по соединениям** (`nf_conntrack_acct`): процесс суммировал бы байты по источнику. Отклонено: соединение уходит из таблицы вместе со своими байтами, и короткие соединения терялись бы между замерами.
- **Только «от устройства» в цепочке prerouting** — запасной вариант на случай, если наборы заметно снизят скорость. Не понадобился.

## Решение

- **Шесть наборов `dv_*`** (Туннель, Напрямую, Входящие × к устройству и от него) в обеих таблицах Трубы. Ключ — IPv4 устройства со стороны Роутера: источник для «от устройства», назначение для «к устройству». Элемент живёт сутки после последнего пакета, наборов не больше 1024 элементов.
- **В каждом правиле `stats` сначала именованный счётчик Действия, затем `update`.** Когда набор полон, `update` нового адреса прерывает правило, и `return` не срабатывает. Правила не пересекаются (явные `ct direction` и интерфейсы с обеих сторон): пакет из прерванного правила больше ни с чем не совпадёт. Общие счётчики верны всегда, новое устройство при полном наборе просто не появляется в списке.
- **Процесс `truba stats`** раз в 5 с читает наборы — каждый своим `nft -j list set`. Несколько `list set` в одном вызове находят только последний набор, а `list table` читает и подсети geoip: 330 мс против 3 мс на набор (замер на x86).
- **История — в `devices.json` в `/var/run`**, переписывается каждый замер. По адресу: скорость, поминутные средние за час, почасовые суммы байт за сутки, время последнего трафика. Флеш не изнашивается, после перезагрузки наборы и так пустые; перезапуск процесса продолжает историю из файла.
- **Применение настроек перезагружает таблицу**, и элементы начинаются с нуля. Замер сравнивается только с замером того же поколения таблицы (`applied.time`), иначе — пропуск шага, а не скачок. Значения наборов, в отличие от именованных счётчиков, в новую таблицу не переносятся.
- **Устройство без трафика дольше суток**, которого нет в наборах, из истории удаляется. Минута без трафика не пишется: адреса живут в наборах сутки, и у сотен устройств без трафика были бы сотни точек нулей.
- **Список `devices` ограничен 256 самыми недавними устройствами и всеми с Политикой.** В наборах может быть до 1024 адресов, в том числе подменённых, а ответ ubus и вкладка столько не вынесут. Интерфейс адресов без соседа ищется по таблицам маршрутов одним вызовом `ip`, а не процессом на адрес.
- **Из нескольких секций `device` с одним MAC действует первая** — в наборах ядра, в списке и на вкладке одинаково.

## Последствия

- Цена по замеру на NC-1812 (Туннель и Напрямую, с наборами и без): ни одно ядро не занято больше 29 %, `sirq` самого загруженного ядра вырос не больше чем на 1 пункт. Скорость упирается в канал, а не в Роутер.
- Процесс `stats` запускает шесть `nft` раз в 5 с сверх прежних.
- Каждое применение настроек даёт по устройствам один пропущенный шаг.
- Пакеты соединений, ускоренных flowtable, идут мимо `stats` — по устройствам, как и в общем учёте, их нет.
- Учёт по устройствам — только IPv4, как вся Маршрутизация (ADR 0005).

## Пересмотреть, если

- в домашней сети больше 1024 адресов за сутки;
- нужно хранить историю дольше суток или переживать перезагрузку;
- nftables научится читать несколько наборов одним вызовом без всей таблицы;
- учёт понадобится и для IPv6.
