# Проверки — в Docker на настоящей ImmortalWrt, независимыми частями параллельно

- Статус: принято

## Контекст

Труба — это в основном связки чужих программ: procd, netifd, fw4, nftables, dnsmasq, mosdns, rpcd, LuCI. Ошибки живут на стыках: порядок цепочек и приоритеты меток, кто перезапускает mosdns, что видит rpcd после HUP, что делает LuCI при «Сохранить и применить». Моки этих программ проверили бы только наши ожидания от них. Настоящий Роутер в CI не поставить, а эмулировать его целиком (qemu) медленно.

Одна большая последовательная проверка на одном стенде шла больше шести минут: сценарии ждали друг друга, а между шагами стояли паузы по таймеру.

## Решение

- **Настоящая ImmortalWrt в Docker.** Стенд — rootfs `immortalwrt/rootfs` той же ветки 25.12 под настоящим procd/netifd/fw4 с `--privileged`. Туннель — настоящий WireGuard до netns «VPS», домашняя сеть — netns за `br-lan`. Модули ядра хоста, которых нет на стенде (amneziawg, иногда `nft_socket`), заменяются или проверка пропускается явно (`skip`).
- **Три уровня.** Логика без ядра и служб — модульные проверки на ucode (секунды): план, Приоритет, генерация правил против эталонов (`tests/golden`, плюс `nft -c`), разбор настроек, «Проверить домен/IP» на синтетических Наборах правил, история скорости. Ядро и службы — сценарии на стенде Роутера. Интерфейс — живой стенд LuCI и headless Chromium.
- **Независимые части.** Сценарии Роутера разбиты по темам (путь пакетов, DNS, списки, отказы, Туннель, история скорости); у каждой свой стенд, и все идут параллельно: локально — фоном из `tests/run.sh`, в CI — отдельными заданиями одной матрицы `tests.yml`. Её же вызывает `build.yml` перед публикацией фида.
- **Ожидание по условию, а не по таймеру.** После `reload` правила уже в ядре; то, что procd делает сам, ждётся проверкой состояния. Готовность стенда — маркер из `/etc/rc.local`.
- **Детерминированные входные данные.** Наборы правил на PR — закреплённые выпуски (`tests/dat.pin`, проверка SHA-256, кэш); свежие — каждый день отдельной задачей. Для DNS — подставные серверы и синтетические Категории вместо интернета.
- **Образы — из кэша, а не из Docker Hub.** Роутер — последняя ImmortalWrt 25.12.x (плавающий тег: проверки идут на той ветке выпусков, что ставят на Роутер), браузер — по дайджесту. В CI образы, в том числе образ Роутера с зависимостями Трубы, хранятся в `actions/cache` и обновляются раз в неделю: общий для раннеров GitHub лимит Docker Hub не роняет проверки, а зависимости не ставятся в каждом задании заново.

## Последствия

- Проверки на PR занимают столько, сколько самая долгая часть (около полутора-двух минут), а не сумму всех.
- Каждая часть платит за свой стенд (секунд десять) — это дешевле, чем ждать соседние сценарии.
- Изменение генерации правил видно в диффе эталонов: новое поведение — новые эталоны в том же коммите.
- Нужен Docker с `--privileged`; на Windows — Git Bash (`run.sh` сам переводит пути).
- Особенности стенда (часовой пояс +0800, зоны, на которые dnsmasq отвечает сам, отбрасывание частных ответов) описаны в `tests/README.md`; сценарии обходят их явно.

## Пересмотреть, если

- появится сборка с модулем amneziawg под ядро раннера — тогда Туннель на стенде может стать настоящим AmneziaWG;
- образ `immortalwrt/rootfs` перестанет выходить для нужной ветки — тогда стенд собирается из ImageBuilder;
- какая-то часть станет заметно дольше остальных — её делят дальше.
