# ubus-API Трубы — в пакете `truba`, объект регистрирует один плагин

- Статус: принято

## Контекст

ubus-объект `truba` (rpcd-плагин: `status`, `rates`, `check`, проверки в фоне…) — тонкая обёртка над командной строкой `truba`. Если API лежит в `luci-app-truba`, а CLI — в `truba`, они меняются вместе, а версии пакетов — порознь: новый интерфейс может встать на старую службу, у которой ещё нет нужной команды. Без LuCI объекта не было бы вовсе, и скрипты или уведомления не могли бы спросить состояние через ubus.

У rpcd (2026.07.19, `ucode.c`) есть ошибка: если два плагина регистрируют один объект, неудавшуюся регистрацию он освобождает, но оставляет в своём списке, и следующий плагин пишет в освобождённую память. Порядок загрузки плагинов — как отдаёт `readdir`, а не по имени. На NC-1812 rpcd от этого падал на HUP (код 139), procd переставал его поднимать, и LuCI не пускал: вход отвечал RPCError и «неверный пароль». В Docker на x86 и в эмуляции aarch64 падение не воспроизводится.

## Решение

- Плагин лежит в пакете `truba`: `/usr/share/rpcd/ucode/truba-api.uc`, зависимость — `rpcd-mod-ucode`.
- `luci-app-truba` — только интерфейс: представления, меню, ACL, перевод. Он зависит от `truba` той же версии, и оба пакета обновляются вместе.
- Объект `truba` регистрирует ровно один плагин — `truba-api.uc`.
- postinst `truba` шлёт rpcd HUP: rpcd перезапускается сам и сохраняет сессии LuCI. postrm тоже шлёт HUP.

## Последствия

- API и CLI — в одном пакете и одной версии. Проверка `luci` сверяет вызовы интерфейса с методами плагина и с ACL.
- `ubus call truba status` работает и без LuCI. Права на методы задаёт ACL интерфейса; без `luci-app-truba` объект доступен только root.
- Новые плагины Трубы не должны повторять имя объекта, даже временно. Падение на x86 не воспроизводится, поэтому тест его не поймает — правило держится на ревью.

## Пересмотреть, если

- в rpcd исправят повторную регистрацию объекта.
