# ubus-API Трубы — в пакете `truba`, а не в интерфейсе

- Статус: принято
- Дата: 2026-10-09

## Контекст

ubus-объект `truba` (rpcd-плагин: `status`, `rates`, `check`, проверки в фоне…) лежал в `luci-app-truba`, а вызывал командную строку `truba` из соседнего пакета. Зависимость была `truba (>=0)`. API и CLI менялись вместе, а версии пакетов — порознь: новый интерфейс мог встать на старую службу, у которой ещё нет нужной команды (например, `rates` до r16). Без LuCI объекта не было вовсе, и скрипты, а в будущем уведомления, не могли спросить состояние через ubus.

## Решение

- Плагин переезжает в пакет `truba`: `/usr/share/rpcd/ucode/truba-api.uc`. Он зависит от `rpcd-mod-ucode`, а postinst и postrm перезапускают rpcd по HUP (rpcd по HUP перезапускается сам и сохраняет сессии).
- `luci-app-truba` остаётся интерфейсом: представления, меню, ACL. Зависимость — `truba (>=1.0.0-r17)`.
- Имя файла — не `truba.uc`. Под этим именем плагин лежал в `luci-app-truba` до r14, а apk не даёт двум пакетам один путь: `truba` ставится раньше зависящего от него интерфейса. Пока старый интерфейс ещё стоит, rpcd загружает его плагин вторым (по имени), регистрация того же объекта не проходит, и объект остаётся за новым.

## Последствия

- API и CLI — в одном пакете и одной версии. Проверка `luci` в тестах сверяет вызовы интерфейса с плагином из пакета `truba`, а CI — зависимость с версией из Makefile.
- `ubus call truba status` работает и без LuCI.
- Права на методы задаёт ACL интерфейса. Без `luci-app-truba` объект доступен только root через ubus.
