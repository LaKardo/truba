# Подъём и падение Туннеля — полное применение настроек, а не точечные правки

- Статус: принято (действует с первой версии, записано 2026-10-09)
- Дата: 2026-10-04

## Контекст

От состояния интерфейса Туннеля зависит больше, чем таблица 77: адрес и подсеть Туннеля (`bypass4`, адрес Трубы внутри Туннеля для проверки), имя устройства (`rp_filter`, правило `oif`), IP Трубы, если endpoint задан именем (цепочка `output`, `bypass4`, внешний адрес UPnP). При загрузке служба стартует (`START=99`) раньше, чем поднимется Туннель и заработает DNS. После «Импорт .conf» меняются адрес, endpoint и ключи. Точечные обработчики для каждого случая — второй путь применения рядом с `reconcile`, который легко рассинхронизировать с первым.

## Рассмотренные варианты

- **Точечные правки по событию:** пересчитать только таблицу 77 и `bypass4`. Дешевле, но всё остальное (IP Трубы по имени, цепочка `output`, UPnP, `rp_filter`) нужно отслеживать отдельно.
- **Полное применение по событию** (`procd_add_interface_trigger … reload`) — выбрано.

## Решение

- `service_triggers` вызывает `reload` при каждом событии интерфейса Туннеля. `reload` — это тот же `truba apply`, что и «Сохранить и применить».
- hotplug (`50-truba`) остаётся для мгновенной реакции: пересчитывает таблицу 77 и `bypass4`, пока procd ещё не запустил `reload`.
- Дорогие шаги apply и так пропускаются, пока не изменились их входные данные: распаковка — по отпечатку файлов, перезапуск mosdns — по метке поколения. Счётчики и IP из DNS переносятся в новую таблицу (для IP — с оставшимся сроком, ADR 0007).

## Последствия

- Один путь применения: состояние после события такое же, как после «Сохранить и применить».
- Каждое падение и подъём Туннеля — полная перезагрузка таблицы `inet truba` с подсетями geoip. Перезапуск интерфейса контролем Туннеля — два применения. Это принято: таблица меняется атомарно, открытые соединения держат путь через ct mark.
- Пересмотреть это стоит, только если применение станет заметно дорогим на Роутере или Туннель начнёт часто «моргать».
