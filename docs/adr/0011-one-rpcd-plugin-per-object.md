# Объект `truba` регистрирует один плагин: при старом интерфейсе — его

- Статус: принято
- Дата: 2026-10-09
- Уточняет: [ADR 0008](0008-ubus-api-in-truba-package.md), пункт про смешанные версии

## Контекст

С r17 ubus-API лежит в пакете `truba` как `truba-api.uc` (ADR 0008). До r14 тот же объект `truba` регистрировал плагин `luci-app-truba` — `truba.uc`. Пакеты обновляются порознь: у r13 интерфейса зависимость `truba (>=0)`, поэтому можно обновить одну службу, и оба плагина окажутся рядом.

ADR 0008 считал это безопасным: второй плагин не зарегистрирует объект, и тот останется за первым. На деле rpcd (2026.07.19, `ucode.c`) добавляет объект в свой список до регистрации, а при неудаче освобождает его, не убрав из списка. Следующий плагин пишет в освобождённую память. Порядок плагинов — как отдаёт `readdir`, а не по имени. Падает ли rpcd, зависит от раскладки памяти. В Docker на x86 и в эмуляции aarch64 он работал. На Роутере (NC-1812) после обновления `truba` до r17 при `luci-app-truba` r13 rpcd упал на HUP из postinst (код 139). procd перестал его поднимать после шести падений, и LuCI не пускал: вход отвечал RPCError и «неверный пароль».

## Рассмотренные варианты

- **Зависимость, которая обновляет интерфейс вместе со службой** (`!luci-app-truba<1.0.0-r14` в зависимостях `truba`). Работает, только если apk решает обе версии вместе, и не спасает при установке из файла.
- **Удалять старый `truba.uc` из postinst `truba`.** Это файл чужого пакета: apk теряет его из учёта, а старый интерфейс остаётся без API.
- **Новый плагин уступает объект, пока стоит старый** — выбрано.

## Решение

- `truba-api.uc` при загрузке проверяет `/usr/share/rpcd/ucode/truba.uc`. Если файл есть, плагин возвращает пустой набор объектов и не регистрирует ничего. Объект остаётся за старым плагином, и старый интерфейс работает с ним как раньше: CLI `truba` совместим.
- Обновление `luci-app-truba` до r14 удаляет `truba.uc`. HUP из его postinst перезапускает rpcd, и объект регистрирует `truba-api.uc`.
- postinst `truba` (r18) шлёт rpcd HUP, а если rpcd не запущен, перезапускает его. Тогда Роутер, который r17 оставил без rpcd, возвращает LuCI обновлением `truba` по SSH.

## Последствия

- Два плагина одного объекта больше не регистрируются ни при каком порядке обновления. Интеграционный тест кладёт подставной старый плагин и проверяет, что объект за ним, `truba-api.uc` не регистрирует ничего, а rpcd переживает HUP. Падение само на x86 не воспроизводится, поэтому тест проверяет отсутствие второй регистрации, а не падение.
- Пока стоит интерфейс до r14, работает его версия API. Методов, которых в ней нет, нет и у объекта.
- Тем, у кого rpcd уже лежит: перезагрузить Роутер (при чистом запуске rpcd обычно поднимается) или по SSH `apk update && apk upgrade truba luci-app-truba luci-i18n-truba-ru`, затем, если вход не появился, `/etc/init.d/rpcd restart`.
- Ошибка в rpcd остаётся. Любые два плагина с одним объектом могут его уронить, и новые плагины Трубы не должны повторять имя объекта, даже временно.
