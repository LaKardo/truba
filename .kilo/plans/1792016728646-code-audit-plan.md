# План: Аудит кода проекта Truba на ошибки и устаревшую информацию

## Сводка

Проведён полный аудит кодовой базы проекта Truba (версия 1.2.0-r3) на наличие:
- ошибок и багов
- устаревшей информации
- мёртвого кода
- лишнего кода

## Обнаруженные проблемы

### 1. **КРИТИЧЕСКАЯ: Анахронизм в датах (будущее время)**

**Проблема:** Проект содержит даты из 2026 года, хотя сейчас октябрь 2026 года, а проект описывается как "версия 1.2.0 — 2026-10-14". Это выглядит странно, так как:

- `CHANGELOG.md:13`: `## 1.2.0 — 2026-10-14`
- `CHANGELOG.md:136`: `## 1.1.0 — 2026-10-10`
- Множество ADR с датами 2026-10-10 до 2026-10-12
- Тестовые данные с `2026-10-04` и другими датами 2026 года
- Коммент в `uplot.js:2`: `Copyright (c) 2025, Leon Sorokin`

**Вопрос:** Это реальная дата или проект создан с тестовыми/будущими датами? Нужно уточнить у пользователя.

**Действие:** Если даты неверные, заменить на актуальные; если это преднамеренно (проект разрабатывается в 2024), оставить как есть.

### 2. **Потенциальная проблема: ImmortalWrt 25.12.2**

**Проблема:** Проект жёстко привязан к ImmortalWrt версии 25.12.x, но:

- `router/VERSIONS` содержит только `25.12.2`
- В коде нет проверок на будущие версии 25.12.3, 25.12.4 и т.д.
- CI workflow `watch-releases.yml` отслеживает новые версии 25.12.x, но неясно, будет ли всё работать с 25.13 или 26.x

**Вопрос:** Как будет обрабатываться переход на ImmortalWrt 26.x? Нужна ли миграционная стратегия?

**Действие:** Добавить в roadmap.md пункт о совместимости с будущими мажорными версиями ImmortalWrt.

### 9. **Hardcoded пути и magic numbers**

**Примеры:**
- `10.77.77.1` — адрес VPS в туннеле (захардкожен везде)
- `/var/run/truba/` — пути к runtime-файлам
- `0x0f000000` — биты меток nftables

**Проблема:** Если в будущем понадобится изменить, придётся менять во многих местах.

**Статус:** Частично решено в ADR 0015 (single source schema), но:
- Адрес туннеля `10.77.77.1` остаётся магическим
- Биты меток — настройка только "если другая служба займёт `0x0f000000`" (ADR 0011), но нет механизма настройки

**Действие:** Всё задокументировано в ADR. Реальная проблема возникнет только при конфликте, тогда пересмотреть.

### 10. **Отсутствие версионирования API между truba и luci-app-truba**

**Проблема:** 
- `luci-app-truba` 1.2.0-r3 требует `truba` >= 1.2.0-r1
- Но в коде нет явной проверки версии API
- `truba.schema` может измениться, а LuCI просто сломается

**Файл:** `router/luci-app-truba/Makefile:13`

```makefile
EXTRA_DEPENDS:= truba (>= 1.2.0-r1)
```

**Действие:** Добавить в `truba.schema` поле `api_version` и проверять его в LuCI при инициализации.
